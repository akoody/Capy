# 0002. Глобальный guard по initData Telegram

- Статус: принято
- Дата: 2026-11-06
- PR: [#2](https://github.com/akoody/Capy/pull/2)

## Контекст
Mini App получает от Telegram строку `initData`, подписанную токеном бота. Прежняя middleware:
- сравнивала HMAC через `===`, то есть не за постоянное время;
- не проверяла `auth_date`, и перехваченный initData работал бессрочно;
- делала `JSON.parse` без обработки ошибок, битые данные давали 500;
- клала в запрос нетипизированный `any`;
- висела на `*`, публичный маршрут сделать было нельзя.

## Решение
- `verifyTelegramInitData()` реализует как чистую функцию [алгоритм Telegram](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app): `timingSafeEqual`, срок жизни `TELEGRAM_AUTH_MAX_AGE_SECONDS` (сутки, допуск 60 секунд на расхождение часов), zod-схема пользователя. Возвращает тип-объединение с причиной отказа, а не бросает исключения.
- `TelegramAuthGuard` подключён через `APP_GUARD`. Просрочка даёт 401 (клиент переоткрывает приложение), неверная подпись даёт 403. `@Public()` отключает проверку для отдельных маршрутов.
- После проверки guard находит или создаёт аккаунт через порт `AccountResolver` (реализует `UsersService`) и кладёт `request.account` (см. [0003](0003-owner-scoped-data-access.md)).
- CORS выключен, пока не задан `CORS_ORIGINS`: фронт и API работают на одном домене за nginx.

## Рассмотренные варианты
- **Свой JWT после обмена initData**: даёт короткоживущие токены и отзыв, но добавляет эндпоинт обмена, хранение секрета и обновление токена. Для Mini App, где initData и так приходит при каждом открытии, это лишняя сложность.
- **Passport-стратегия**: ещё один слой абстракции вокруг одной HMAC-проверки.

## Последствия
- Логика проверки покрыта unit-тестами без моков (время передаётся параметром), guard проверен HTTP-тестами через supertest.
- initData живёт сутки: если пользователь держит приложение открытым дольше, клиент получит 401 и должен переоткрыть Mini App.
