# 0008. Базовая эксплуатация: пробы, логи, лимиты, контейнеры

- Статус: принято
- Дата: 2026-11-09

## Контекст
API запускался через pm2 и shell-скрипты. Логи были текстовыми и не связывались с запросом, состояние процесса снаружи не проверялось, общего ограничения частоты запросов не было.

## Решение
- `/health` проверяет только процесс, `/ready` дополнительно проверяет ответ MongoDB. Обе точки публичные и не считаются в лимит.
- Логи в JSON через pino. Каждый запрос получает `x-request-id`, входящий заголовок сохраняется. `Authorization`, cookie и query в логи не попадают.
- Лимит считается на аккаунт после проверки подписи Telegram, на публичных маршрутах — на IP.
- Один образ для API и воркера, отдельный образ nginx со статикой. `compose.yaml` поднимает MongoDB как replica set из одного узла, потому что без него не работают транзакции.
- OpenAPI генерируется из контроллеров и DTO на `/docs`. По умолчанию выключен.

## Рассмотренные варианты
- **Лимит на IP** — за одним адресом мобильного оператора находятся тысячи пользователей Mini App, и они исчерпывали бы общий лимит.
- **`@nestjs/terminus`** — полезен при нескольких зависимостях, для одного ping базы это лишний пакет.
- **Redis для счётчиков** — точный лимит при нескольких экземплярах, но это новый компонент инфраструктуры (см. ADR-0007) ради защиты от злоупотреблений, которой не нужна точность.

## Последствия
- Счётчики лежат в памяти процесса: при N экземплярах API фактический лимит в N раз выше. Перед масштабированием за несколько машин счётчики нужно вынести в общее хранилище.
- Запросы с неверной подписью отклоняются до лимита. Они дешёвые (только HMAC), защиту от объёмного трафика даёт nginx.
- `compose.yaml` рассчитан на одну машину. MongoDB в нём без авторизации и доступна только во внутренней сети контейнеров.
