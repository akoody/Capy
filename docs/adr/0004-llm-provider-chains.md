# 0004. LLM-провайдеры за одним модулем с цепочками fallback

- Статус: принято
- Дата: 2026-11-07
- PR: [#4](https://github.com/akoody/Capy/pull/4)

## Контекст
Анализ транзакций, копилки и журнала содержал три одинаковые копии клиента для GigaChat → Gemini → DeepSeek → Groq: четыре вложенных `try/catch`, ответы `axios` с типом `any`, токен GigaChat в `(this as any)`. Ассистент держал пятую копию с OpenAI первым и другими параметрами. На этих копиях было больше половины из 602 ошибок линтера. Внутри нашлись баги: токен GigaChat запрашивался на каждый вызов (срок читался из несуществующего поля), TLS к GigaChat не проверялся без всякого предупреждения, ключ Gemini передавался в URL.

## Решение
Модуль `src/llm`:
- `LlmProvider`: интерфейс адаптера; реализации `GigaChatProvider`, `GeminiProvider` и `OpenAiCompatibleProvider` (OpenAI, DeepSeek, Groq) с типизированными ответами;
- `LlmService.complete(prompt, options, purpose)` пробует настроенных провайдеров по порядку и, если никто не ответил, бросает `LlmUnavailableError` со списком отказов;
- две цепочки по назначению: `analysis` (GigaChat, Gemini, DeepSeek, Groq) и `interpret` (OpenAI с JSON-режимом, затем те же). Состав цепочек собирается в `LlmModule` из конфига;
- проверка TLS для GigaChat включается через `GIGACHAT_CA_CERT_PATH`; пока сертификат не задан, при старте пишется предупреждение.

## Рассмотренные варианты
- **SDK каждого провайдера**: пять зависимостей с разными моделями ошибок ради одного POST-запроса на провайдера.
- **Общий шлюз вроде LiteLLM**: отдельный сервис в инфраструктуре; оправдан при десятках моделей или учёте стоимости, здесь избыточен.

## Последствия
- Минус ~870 строк дублирования; поведение (модели, параметры, порядок) сохранено.
- Провайдеры тестируются с подменой `axios`: формат запроса, ошибки, кэш токена GigaChat.
- Чтобы добавить провайдера, нужны один адаптер и одна строка в цепочке.
- Распознавание речи вынесено в отдельный `SpeechToTextService` со своей цепочкой OpenAI и Groq Whisper.
