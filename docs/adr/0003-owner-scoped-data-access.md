# 0003. Владелец данных только из подписи, доступ через `ownedBy`

- Статус: принято
- Дата: 2026-11-07
- PR: [#3](https://github.com/akoody/Capy/pull/3)

## Контекст
Аутентификация работала, авторизации не было. Большинство маршрутов брали владельца из запроса: `GET /transactions?userId=`, `PATCH /piggy-bank/deposit` с `userId` в теле, `GET /users/:id/export`, `PATCH /users/:id` с произвольным телом, а операции по `:id` искали запись через `findById` без проверки владельца. Любой вошедший пользователь мог читать и менять чужие финансы, выгружать чужие данные и выставлять себе очки.

## Решение
- **Один источник владельца.** `@CurrentUserId()` читает `request.account.userId`, который заполняет guard. Поля `userId`, `user`, `requesterId` убраны из DTO; `whitelist` отбрасывает их, если клиент их пришлёт.
- **Единый контракт сервисов.** Методы принимают `userId` первым аргументом. Запросы по id идут через `ownedBy(userId, id)` из `src/common/owned-by.ts`.
- **404 вместо 403.** Чужая, несуществующая и некорректная запись дают одинаковый ответ, чтобы нельзя было перебором узнать, какие id существуют.
- **Профиль через `/users/me`.** Изменять можно только явно перечисленные поля (`currency`, `language`). Каталог пользователей удалён, лидерборд и друзья отдают только публичные поля.
- **Связи проверяются.** Транзакцию нельзя привязать к чужой цели, отвечать на заявку в друзья может только получатель.
- **Аккаунт создаётся атомарно.** `findOneAndUpdate` с `upsert` по уникальному `telegramId`, поэтому параллельные первые запросы не создают дублей.

## Рассмотренные варианты
- **Проверка владельца в guard или interceptor по параметру маршрута**: guard не знает, какой коллекции принадлежит `:id`. Пришлось бы описывать соответствие метаданными на каждом маршруте, а ошибка в метаданных снова откроет дыру.
- **Mongoose-плагин, добавляющий `user` в каждый запрос**: неявное поведение через контекст запроса (AsyncLocalStorage) сложнее отлаживать, и он не помогает там, где владелец хранится в другом поле (`requester`/`recipient`).

## Последствия
- Правило видно в каждом методе сервиса, его легко проверить на ревью.
- Поведение закреплено e2e-тестами на MongoDB: второй пользователь пытается читать, менять и удалять данные первого. Тест проверен на регрессию: если вернуть `findById`, он падает.
- Новые модули обязаны следовать контракту, это проверяется на ревью.
